Problem Definition

National Scale & Engineering Challenges

Standardizing India's 5-tier administrative boundaries for B2B APIs

Ξ
Geographic Volume
  • 36 States and Union Territories
  • 700+ Administrative Districts
  • 6,000+ Sub-Districts / Talukas
  • 600,000+ Revenue Villages
  • Raw dataset exceeds 650,000 rows requiring zero-loss ingestion.
Δ
Integrity Vulnerabilities
  • Leading Zero Loss: Casting MDDS codes as numbers strips leading zeroes (e.g., 03950 becomes 3950).
  • Orphan Drift: Lack of strict foreign keys creates disconnected villages.
  • Unnormalized Bloat: Storing state/district on village rows creates update anomalies.
Ω
B2B Product Objectives
  • Low Latency: Sub-50ms fuzzy address autocomplete across 600k rows.
  • Multi-Tenancy: Tiered quotas (Free, Starter, Enterprise).
  • Row-Level Security: Restricting client keys to authorized states via UserStateAccess.

Database Engineering

Third Normal Form (3NF) Relational Architecture

Strict 5-tier geographic lineage with multi-tenant access control

1. Geographic Lineage (3NF)
Country (IND) → State (36) → District (700+) → SubDistrict (6k+) → Village (600k+)
  • Zero Transitive Redundancy: Villages reference only their immediate parent subDistrictId, never State or Country.
  • Referential Protection: Strict ON DELETE RESTRICT prevents accidental deletion of populated jurisdictions.
  • Leading Zero Retention: All codes defined as VARCHAR(10) so 03950 is never truncated to 3950.
2. Identity, B2B Auth & Telemetry
  • User: Enterprise accounts with bcrypt password hashes and tiered plans (FREE, ENTERPRISE).
  • ApiKey: Salted SHA-256 keyHash with human prefix (ba_live_) for O(1) auth.
  • UserStateAccess: Row-level regional access control table restricting client keys to approved States.
  • ApiLog: High-throughput append-only audit trail capturing latency, endpoint, IP, and status code.
Speaker: "Our 3NF relational schema completely eliminates update anomalies. We have also built in enterprise B2B multi-tenancy with UserStateAccess and ApiLog."

ETL Engineering

High-Speed Streaming ETL Pipeline

Ingesting ~650,000 MDDS records in <4 minutes with zero memory exhaustion

Streaming Ingestion Mechanics
  • In-Memory Parent Cache: States, Districts, and Sub-Districts are cached in local RAM hash tables, eliminating 600,000+ individual SELECT roundtrips.
  • Streamed Chunking: Raw records read in 50,000-row chunks using Pandas generators; keeps memory watermark strictly under 250 MB.
  • Bulk Batch Inserts: 5,000 village rows committed per transaction using PostgreSQL execute_values.
Fault Isolation & Dead-Letter Queue
  • Dead-Letter Quarantine: Malformed rows missing codes are routed to quarantine_records.jsonl without failing the batch.
  • Atomic Rollback: Database socket or disk errors roll back only the active 5k chunk with exponential retry.
  • Post-Load Maintenance: Automatically executes VACUUM ANALYZE to prime PostgreSQL's cost-based query optimizer.
Speaker: "Traditional bulk imports fail on memory or timeout. By caching parent IDs in RAM and streaming chunks of 5,000, we load 650k rows in under 4 minutes with zero orphans."
