1. Executive Summary & Problem Context

This technical specification documents the Phase 1 engineering deliverables for the MDDS Administrative Hierarchy & B2B Location Intelligence Platform. The system provides high-throughput address resolution, administrative lineage queries, and fuzzy location search covering over 600,000 revenue villages across India, standardized against the Ministry of Drinking Water and Sanitation (MDDS) catalogs.

Core Engineering Mandate: Eliminate geographic duplication and orphaned records through a Third Normal Form (3NF) relational database, deliver sub-50ms fuzzy search latency, and provide a memory-safe ingestion engine capable of loading ~650,000 records in under 4 minutes.

2. Technical Architecture & Stack Decision Matrix

The stack selections balance developer velocity, serverless horizontal elasticity, edge caching, and strict relational integrity:

Layer Selected Tech Architectural Rationale Production Safeguard
Backend Runtime Node.js (LTS) + Express.js Asynchronous, non-blocking event loop optimized for I/O-bound REST lookups. Heavy ETL compute decoupled to dedicated Python worker.
Primary Database NeonDB (PostgreSQL 16) Serverless autoscaling, instant branch environments, and pgBouncer pooling. Hot read paths absorbed by Upstash Redis edge cache.
ORM / Data Layer Prisma ORM Compile-time type safety, declarative migrations, and 3NF schema enforcement. Bulk operations use raw SQL / COPY batches.
Edge Caching Upstash Redis Global sub-millisecond edge cache with HTTP REST interface (zero TCP leaks). 24h TTL on static hierarchy queries; LRU eviction.
Rate Limiting Sliding Window (Redis) Distributed rate limiting across edge lambdas to enforce tier-based API quotas. In-memory fallback if Redis is momentarily unreachable.
Authentication JWT + SHA-256 Hashes Stateless bearer tokens for dashboard; salted SHA-256 hashes for API credentials. Short 15m JWT TTL with Redis revocation blocklist.

4. Database Design & Relational Schema (3NF)

The database follows strict Third Normal Form principles to ensure referential integrity and prevent data anomalies:

Critical Data Integrity Safeguard: All MDDS code fields (MDDS STC, MDDS DTC, MDDS Sub_DT, MDDS PLCN) are enforced strictly as VARCHAR strings. Numeric casting strips vital leading zeroes (e.g. Sub-District 03950 is corrupted to 3950), breaking government compliance.

Relational Hierarchy Lineage

Country (IND)
  └─ State (MDDS STC: "27" - Maharashtra)
      └─ District (MDDS DTC: "497" - Nandurbar)
          └─ SubDistrict (MDDS Sub_DT: "03950" - Akkalkuwa)
              ├─ Village: Manibeli   (MDDS PLCN: "525002")
              ├─ Village: Dhankhedi  (MDDS PLCN: "525003")
              ├─ Village: Chimalkhadi (MDDS PLCN: "525004")
              └─ Village: Sinduri    (MDDS PLCN: "525005")

Each table maintains strict foreign key relationships with ON DELETE RESTRICT on geographic tables to prevent accidental deletion of populated jurisdictions.

5. Performance Indexing Strategy

To maintain sub-50ms response times across 600,000+ village rows, specialized indexes are implemented based on access patterns:

Table Indexed Column(s) Index Method Optimized Query Pattern
villages name GIN (gin_trgm_ops) Sub-50ms fuzzy autocomplete using PostgreSQL pg_trgm (WHERE name ILIKE '%mani%').
villages (sub_district_id, name) Composite B-Tree Instant alphabetical pagination within a specific Sub-District.
api_keys key_hash Unique B-Tree / Hash Constant-time O(1) API credential validation in gateway middleware.
api_logs (created_at DESC, user_id) Composite B-Tree High-speed time-series analytics, billing calculations, and usage telemetry.

6. Streaming MDDS Ingestion Engine (~650,000 Rows)

Traditional bulk imports suffer from memory leaks and gateway timeouts. The custom Python engine implements three optimizations:

  1. In-Memory Parent Cache: Existing State, District, and SubDistrict UUIDs are cached in local hash tables, eliminating 600,000+ individual SELECT queries.
  2. Streamed Chunking: Files are read in 50,000-row chunks using Pandas generators, capping RAM consumption at <250 MB.
  3. Batch Transaction Commits: Multi-row inserts are executed in chunks of 5,000 records using PostgreSQL execute_values, completing full ingestion in under 4 minutes.
  4. Dead-Letter Quarantine: Malformed rows missing codes are routed to quarantine_records.jsonl without failing the batch.
